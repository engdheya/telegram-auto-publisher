## 1. لماذا لا يمكن تنفيذ هذه الفحوص من داخل بيئة التطوير هذه

الفحوص السبعة التي طلبتها (1→7) تتطلب `MTProto` حقيقيًا بحساب **مصرّح**:

| المتطلب | لماذا لا يمكن توليده | كيف تحصل عليه |
|---|---|---|
| `api_id` / `api_hash` | يُصدرهما تيليجرام لحسابك بعد تسجيل الدخول بجوالك — لا يوجد API عام لتوليدهما | https://my.telegram.org → API development tools |
| رقم الهاتف + رمز OTP | يصل إلى جهازك/تطبيق تيليجرام الخاص بك | جهازك |
| كلمة مرور التحقق بخطوتين (2FA) | يملكها أنت فقط | جهازك |
| قناتان حقيقيتان على الأقل (مصدر + هدف) | لا يمكن للنظام إنشاء قنوات عامة نيابةً عنك | تيليجرام |
| هوية مساعدة (بوت أو حساب مساعد) | البوت يجب أن يُنشأ من @BotFather ويُضاف كمسؤول في القناتين | @BotFather |
| اتصال إنترنت قابل للإسقاط فعليًا | البيئة السحابية هنا لا تسمح بإسقاط الشبكة على عملية حيّة بأمان | جهازك/سيرفرك |

لا يمكن «محاكاة» هذه الخطوات: أي محاكاة تُنتج نفس المشكلة التي رفضتها في المتطلبات (نجاح على fake gateway لا يُثبت شيئًا). لهذا الذي نُفِّذ هو **كل ما يمكن إثباته مسبقًا**: النظام يعمل، الواجهة تعمل ضد الـAPI الحقيقي وقاعدة البيانات الحقيقية، والعامل يعمل، وسكربت الدليل الحقيقي جاهز ومُختبَر منطقيًا.

## 3. المدخلات الناقصة (مخرجات الفحص الفعلي)

منقول حرفيًا من `docs/evidence/06_live_telegram_prerequisites.txt`:

```
PASS | Dashboard login (JWT issued by real API)
FAIL | Telegram account is linked & CONNECTED (from the dashboard flow) | auth_state=UNCONFIGURED @None session=False
PASS | API never exposes the API hash or the session

== 2. live-run prerequisites ==
FAIL | TELEGRAM_API_ID present | missing
FAIL | TELEGRAM_API_HASH present | missing
FAIL | Helper identity for injecting source content (bot token preferred) | missing
FAIL | TAP_SOURCE_CHATS configured | missing
FAIL | TAP_TARGET_CHATS configured | missing
```

## 4. تشغيل الدليل النهائي (خطواتك أنت، ~15 دقيقة)

### 4.1 التحضير مرة واحدة
```bash
# 1) api_id / api_hash من https://my.telegram.org  →  API development tools
# 2) أنشئ قناتين تجريبيتين (أو استخدم قناتين تملكهما):
#      - قناة المصدر  Source   (اسمها مثلًا: TAP Source Test)
#      - قناة الهدف   Target   (اسمها مثلًا: TAP Target Test)
#    اجعل الحساب الذي ستستخدمه مالكًا/مسؤولًا في الاثنتين.
# 3) أنشئ بوتًا مساعدًا من @BotFather  →  خُذ التوكن
#    ثم أضفه كـ Administrator في قناة المصدر (لإرسال المحتوى)
#    وفي القناة الهدف (لإمكانية قراءة ما وصل).
# 4) (اختياري، لفحص عزل الفشل) قناة ثالثة لا يملك فيها الحساب المرتبط حق النشر.
```

### 4.2 ضع القيم في `.env` (الملف غير المرفوع إلى Git)
```dotenv
TELEGRAM_API_ID=1234567
TELEGRAM_API_HASH=0123456789abcdef0123456789abcdef
TELEGRAM_BOT_TOKEN=123456:AA...
TAP_SOURCE_CHATS=@tap_source_test
TAP_TARGET_CHATS=@tap_target_test
# TAP_TARGET_NO_RIGHTS=@some_channel_without_rights
```
(يقرأ السكربت كذلك `TAP_ADMIN_PASSWORD` أو تلقائيًا `INITIAL_ADMIN_PASSWORD` من نفس الملف.)

### 4.3 اربط الحساب من الواجهة (هذا هو الفحص رقم 1 و2)
1. افتح `http://<host>/telegram` (صفحة «حساب تيليجرام»).
2. أدخل `api_id` و`api_hash` ورقم الهاتف بصيغة دولية → **إرسال رمز التحقق**.
3. أدخل رمز OTP الظاهر في تطبيق تيليجرام → **تأكيد**.
4. إن كان الحساب محميًا بكلمة مرور: أدخل كلمة مرور 2FA → **تأكيد**.
5. النتيجة المتوقعة: الحالة تصبح **CONNECTED** واسم الحساب يظهر في اللوحة.

### 4.4 شغّل سكربت الدليل
```bash
# النظام يعمل (API + worker + الواجهة) ثم:
python3 scripts/live_telegram_e2e.py --dry-run   # يتأكد أن كل المتطلبات حاضرة
python3 scripts/live_telegram_e2e.py             # ينفّذ الفحوص 1→7 ويكتب الدليل
```
مخرجات السكربت تُكتب في هذا الملف نفسه (`docs/LIVE_TELEGRAM_EVIDENCE.md`) بقسم
«نتائج التنفيذ الحقيقي» يحتوي كل تأكيد مع معرّفات رسائل تيليجرام الخام.

## 5. ما يفحصه السكربت بالضبط (مطابقة لمتطلباتك)

| متطلبك | الفحص في السكربت |
|---|---|
| 1. حساب حقيقي لا Fake gateway | `Telethon` حقيقي، و`auth_state == CONNECTED` من الـAPI، والفحص يُفشل عند `UNCONFIGURED` |
| 2. ربط الحساب + OTP + 2FA | الربط يتم من الواجهة؛ السكربت يتحقق من `session=True` ومن وجود الحساب بعد الربط |
| 3. تحويل تلقائي مصدر ← هدف | نشر رسالة في المصدر، ثم قراءة القناة الهدف عبر تيليجرام نفسه ومقارنة النص |
| 4. نص، صورة، فيديو، ملف، ألبوم | 5 عمليات نشر منفصلة، كل واحدة تُقارن نوع المحتوى في الهدف |
| 5. 1→N و N→N | مسار واحد إلى عدة أهداف، ثم عدة مصادر إلى عدة أهداف، مع مهمة مستقلة لكل هدف |
| 6. انقطاع ← إعادة اتصال ← استعادة | إيقاف العامل ثم إعادة تشغيله، والتأكد من نشر الرسائل المفقودة (catch‑up) بلا تكرار |
| 7. منع التكرار | التأكد من عدم وجود `publish_jobs` مكرر لكل (رسالة، هدف) وعدم إعادة النشر لهدف نجح |

## 6. ملاحظات أمان

- لا تُرفع أبدًا: `.env`، ملفات `*.session`، قاعدة البيانات، النسخ الاحتياطية، السجلات.
- السكربت يخزّن جلسة الهوية المساعدة **خارج المستودع**: `~/.tap_live_helper.session`.
- السكربت لا يطبع التوكن ولا الـhash ولا الـsession، ولا يكتبها في الدليل.
- بعد الانتهاء، أوقف البوت المساعد واحذف صلاحياته من القنوات إن كانت تجريبية.
